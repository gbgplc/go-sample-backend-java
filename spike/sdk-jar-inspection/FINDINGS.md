# JAR-inspection spike: findings

Investigated `com.gbg:go-core-sdk:0.1.0-alpha01` directly — both a `-sources.jar` and a
`-javadoc.jar` actually resolve from Maven Central (not guaranteed for an alpha release,
but they're there), so every answer below is read from the SDK's real generated source,
not guessed. Source unzipped at `spike/sdk-jar-inspection/extracted/` (gitignored).

Generated by Speakeasy. Every model lives in the single `go-core-sdk` jar — no separate
models artifact (confirmed via `dependency:tree`: only Jackson, SLF4J, reactive-streams,
commons-io, jakarta.annotation-api as runtime deps).

## Q1 — Exception type: resolved, no conflict

Both classes are real and the "conflict" in the docs was two different truths, not a
contradiction: `com.gbg.gocore.models.errors.GoException` is an abstract `RuntimeException`
base with `code()`, `body()`/`bodyAsString()`, `rawResponse()`, `headers()`.
`com.gbg.gocore.models.errors.APIException extends GoException` is the concrete class
actually thrown "on 4XX, 5XX" by every generated operation. `AsyncAPIException` and
`AuthException` also exist. **Catch `APIException`** (or `GoException` if a broader net is
wanted) — accessors are exactly as the top-level README showed.

## Q2 — `StartJourneyRequest`/`Response`: resolved

```java
public class StartJourneyRequest {
    String resourceId;                        // matches current GoStartRequest.resourceId
    StartJourneyContext context;               // optional, structured (typed, not a raw map)
    Map<String, Object> data;                  // optional — the subject-prefill map, untyped
}
```
Constructor `StartJourneyRequest(resourceId)` exists for the no-prefill case. Response is a
`Response`-wrapping envelope (`contentType`/`statusCode`/`rawResponse`/`object`) where
`object()` is `Optional<StartJourneyResponseBody1>` (need `.instanceId()` — not yet read in
depth, but the pattern is identical to `GetJourneyStateResponse` below, so treat as
confirmed-by-pattern).

## Q3 — `GetJourneyStateResponse`: partially resolved, lower risk than feared

```java
public class GetJourneyStateResponseBody {
    String instanceId;
    GetJourneyStateStatus status;              // open enum (see below)
    MetaData metaData;                         // optional
    GetJourneyStateContext context;            // optional, TYPED — journey/identity/document/biometric domain model
    Map<String, Object> data;                  // optional, UNTYPED catch-all
}
```
`GetJourneyStateResult` (Success/Failure/Skipped) is an "open enum" wrapper pattern used
throughout this SDK — `.value()` gives the raw string, `.asEnum()` gives a typed
`Optional<...Enum>`, and an unrecognized value from a future API change doesn't throw, it's
just `!isKnown()`. This pattern repeats for every enum-like field in the SDK.

**Good news for the port**: `data` being an untyped `Map<String, Object>` means the deep,
empirically-verified step/module timing logic in `DefaultInteractionMapper`
(`process.step.durationMilliSec`/`endedAt`, `result.subject.documents[0].classification.name`)
can likely be ported by reading the same paths out of this map via Jackson, the same way the
current code reads the raw Go JSON — NOT by hunting for typed accessors that may not exist
at this granularity. **Not fully confirmed** — whether the step/module list lives under
`context` (typed) or `data` (untyped) needs one live call to see the real populated shape.
Verify in Phase 7's first live run before assuming either.

The domain model under `context` is enormous and fully typed per operation
(`GetJourneyStateDocument`, `GetJourneyStateBiometric1..4`, `GetJourneyStateIdentity`, etc.
— ~150 classes) — far more complete than the current raw-HTTP DTOs, which only model the
handful of fields this app actually reads.

## Q5 — `SubmitInteractionRequest` + document/biometric image data: **resolved, low risk**

This was the single biggest feared gap and it's actually fine:

```java
public class SubmitInteractionRequest {
    String instanceId;
    String interactionId;
    List<Participant> participants;    // { domainElementId, instruction } — matches today's manifest
    SubmitInteractionContext context;  // wraps `subject`
}
```

`SubmitInteractionDocument` (a ~90-field generated class covering every document-extraction
field GBG's modules can populate) has:
```java
private String side1Image;   // exact same field name as today's raw GoInteractionSubmitRequest
private String side2Image;   // exact same field name
```
So document capture submission maps almost 1:1 onto the current hand-rolled shape — same
field names, same base64-string-in-JSON approach, no multipart/binary handling needed
(confirms the current design's assumption was right, it just wasn't documented anywhere).

`SubmitInteractionBiometric1` (one of 4 biometric variants — `Biometric1..4`, a union) has:
```java
private String face1Image;   // NOT "selfieImage" — field name differs from today's code
private String face2Image;
```
**This is a real, small porting change**: today's mapper writes `selfieImage`; the SDK's
biometric model uses `face1Image`/`face2Image`. Confirm which `Biometric` variant (1-4) this
journey's selfie module actually expects before wiring — likely `Biometric1` given the
two-face-image shape matches a standard liveness-check pair, but verify against a live
`collects` response rather than assuming.

`Participant` has an extra optional `instruction` field beyond `domainElementId` — not used
by the current mapper, safe to leave null.

## Q6 — Token generation / grant types: **resolved, better than expected**

Both grant types are modeled as first-class SDK types implementing a shared interface:
```java
com.gbg.gocore.models.ClientCredentialsGrantRequest implements PostAsTokenOauth2Request
com.gbg.gocore.models.PasswordGrantRequest implements PostAsTokenOauth2Request
```
`ClientCredentialsGrantRequest`: `clientId`, `clientSecret`, `grantType` (fixed
"client_credentials"), `scope`. `PasswordGrantRequest`: `clientId`, `clientSecret`,
`username`, `password`, `grantType` (fixed "password") — **no separate scope field**, matching
the current code's `GoTokenService` comment that Keycloak's `password` grant doesn't take
`gbg.token` as a scope.

`PostAsTokenOauth2ResponseBody`: `accessToken` (`access_token`), `expiresIn` (`expires_in`,
`Long`), `tokenType` (`token_type`) — exact match for `GoTokenResponse`.

**Contingency #5 from the plan is lifted**: `sdk.tokens().generate()` genuinely supports both
grants natively. `GoSdkAuthService` should call it directly rather than keeping a raw
form-POST — build a `ClientCredentialsGrantRequest` or `PasswordGrantRequest` per
`GoSdkProperties.grantType()`, same branching logic as today, just swapping the HTTP call for
the SDK call. **Keep the caching wrapper** (`cachedToken`/`cachedTokenExpiresAt`/
`REFRESH_MARGIN_SECONDS`) regardless — nothing in the SDK auto-refreshes.

## Q7 — Server/region selection: **resolved, exact match**

```java
public static final String[] SERVERS = {
    "https://eu.platform.go.gbgplc.com/v2/captain",   // index 0
    "https://us.platform.go.gbgplc.com/v2/captain",   // index 1
    "https://au.platform.go.gbgplc.com/v2/captain",   // index 2
};
```
`serverIndex(0/1/2)` maps exactly to the documented eu/us/au hosts (matches
`GoProperties.baseUrl()`'s composed URL, modulo the SDK's URLs having no trailing slash/
`v2/captain/` segment difference — verify no trailing-slash mismatch causes a 404).
`serverURL(String)` overrides outright — exactly what a tenant like the nonprod fabric one
(different host entirely) needs. `Go` is **immutable once built** — no setter to swap
`customerAccess` post-construction, confirming the plan's default of rebuilding the client on
token rotation rather than trying to mutate an existing instance.

## Q8 — `interactionAccess` vs `customerAccess`: **not fully resolved, best-available answer**

`journeys().start()`/`getState()` javadoc: *"If set, this operation will use
Security#customerAccess from the global security."* — i.e. these two use the client-wide
token from `Go.builder().customerAccess(...)`.

`interactions().submit()`/`fetch()` instead take a **mandatory** (`@Nonnull`) per-call
`SubmitInteractionSecurity`/`FetchInteractionSecurity`, each wrapping a single
`interactionAccess` bearer-token string — a distinct named security scheme from
`customerAccess` at the SDK/OpenAPI-spec level.

No operation in the SDK's full surface (`tokens`, `health`, `devices`, `tasks`, `journeys`,
`instances`, `interactions`) returns anything resembling a scoped "interaction token" —
there is no second credential-issuing call anywhere. The most defensible reading: this is a
Speakeasy/OpenAPI-spec artifact of naming two security schemes differently for
documentation/scoping clarity while both resolving to the same bearer credential on the real
API — consistent with the current raw-HTTP code, which already uses one bearer token for
every endpoint (`journey/start`, `journey/interaction/fetch`, `journey/interaction/submit`,
`journey/state/fetch` alike).

**Recommendation**: pass the same cached access token to `interactionAccess` as to
`customerAccess`. **This is inferred, not proven** — the first live `submit()`/`fetch()` call
in Phase 7 will immediately 401 if it's wrong, which is a cheap, fast way to falsify it.

## Net effect on the plan

- Contingency #5 (keep raw HTTP for token minting) — **lifted**, use `sdk.tokens().generate()`.
- Contingency #1 (no binary/base64 field for capture) — **lifted**, `side1Image`/`side2Image`
  exist with identical names; biometric field names differ (`face1Image`/`face2Image` vs
  today's `selfieImage`) — a rename, not a redesign.
- Contingency #2 (exception ambiguity) — **lifted**, catch `APIException`.
- Contingency #6 (`Go` instance mutability) — **confirmed as suspected**, immutable, rebuild
  per token rotation.
- Contingencies #3, #4, #7 remain genuinely open — the untyped `data` map (Q3), the
  unconfirmed `collects`/`outstanding` equivalents (Q4), and the `interactionAccess` token
  source (Q8) all need one live smoke test each in Phase 7, not further static reading.
